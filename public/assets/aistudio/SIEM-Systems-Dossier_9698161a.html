Model 00 · Executive verdict

A convincing training instrument with a non-functional nervous system.

On the surface the application is a five-workspace security console. Underneath, it is a three-second simulation loop that manufactures two telemetry series, injects three scripted scenarios, and turns investigation into a graded exercise. The pedagogy is the product. The persistence and identity layers are theatre.

This dossier reconstructs the system from five files. It separates what the simulator is from what it claims to be, quantifies the distance, and specifies a rebuild that keeps the teaching loop while replacing everything underneath it. The target is not a real SIEM; it is a production-shaped training environment — deterministic enough to teach, honest enough to grade, and durable enough to survive a page refresh.

Three things are true at once. First, the learner loop is genuinely good: notice an anomaly, inspect the evidence, read a crash course, run a resolution lab, answer a quiz, close the case, and export a report that names the skill practised. That ladder is the most valuable asset in the repository and should be preserved almost intact. Second, the system of record does not exist: the browser holds all state in one mutable object, the database is an optional write-only snapshot, and a refresh erases the workspace. Third, the security posture is inverted — the mock SOC is less protected than the incidents it teaches you to handle.

Blocking defect

The backend cannot start. Every SQL parameter placeholder ($1, $2, …) has been stripped from server.js. All fourteen queries are syntactically invalid, so ensureDefaultAdmin() rejects on boot, the .catch() calls process.exit(1), and the listener never opens. The repository contains zero occurrences of a $n placeholder. This is consistent with the file having been generated through a shell or heredoc that expanded $1 to an empty string.

The verdict in one line

Keep the teaching model. Throw away the persistence and identity layers. Rebuild the shell as a deterministic, local-first application with an optional, properly authenticated collaboration tier.

Five decisions this dossier asks for

  1. Retire the Express tier for v1. Ship the rebuild local-first (IndexedDB) and reintroduce a server only when multi-analyst collaboration is a real requirement. The current API adds attack surface without adding capability.
  2. Model the domain properly. Alerts, cases, evidence, events and audit are different things. Storing them as one JSON blob is the root cause of most defects in this report.
  3. Replace the PIN with identity. A four-digit constant is not access control; it is a prop. Use an identity provider or, at minimum, per-user credentials with server-side sessions.
  4. Move evidence out of state. Screenshots belong in object storage with a reference in the case record, not base64 inside a broadcast message.
  5. Make time and identifiers canonical. UTC ISO-8601 everywhere, opaque server-generated IDs, and a seeded random source so every demo and every test is reproducible.

Model 01 · Context & capability

System at a glance

A single-page simulator with five workspaces, six network segments, three incident scenarios and one very determined three-second clock. Its purpose is to build investigative reflex, not to ingest real logs.

Product thesis

The application teaches a repeatable security-operations reflex: notice → inspect → research → test → resolve → write. It does this by manufacturing a small, legible world. Two metrics — WAN throughput and failed logins per minute — are sampled every three seconds. Three scenarios distort those metrics in recognisable ways. The analyst must read synthetic logs, distinguish attack from accident, choose a proportionate containment, and produce a written case report that records the skill applied.

Everything else in the product exists to serve that loop: the theme engine makes the console feel like a tool, the ticket system gives the exercise a service-desk wrapper, the labs turn multiple choice into guided practice, and the export functions produce artefacts a learner can keep or an instructor can mark.

Every route is wrapped in try/catch and returns err.message with HTTP 500. That is convenient in development and an information-disclosure habit in production: driver errors can reveal table names, column names and constraint details.

The sync path, step by step

  1. Every mutation calls push(), which stamps rev = Date.now()*100 + (seq++ % 100), posts the entire state to BroadcastChannel, optionally POSTs it to the configured backend, then re-renders all five views.
  2. Other tabs receive the snapshot and accept it if rev is higher. Their local state is replaced wholesale; tickets are diffed only to fire notifications.
  3. The backend receives a single JSON body containing state, tickets, audit and feedback. It opens a transaction, updates one row, upserts each ticket, deletes the audit table, inserts 50 audit rows, and inserts feedback with ON CONFLICT DO NOTHING.
  4. The browser never calls GET /api/state. There is no hydration, no reconciliation and no way to recover a session after refresh.
  5. fetch failures are swallowed by catch(_){}. The analyst sees no error, the pill still says “API TARGET SET”, and the database quietly diverges.
Scale consequence

A 900-pixel JPEG at quality 0.6 is typically 80–200 KB; base64 adds roughly a third. With 200 tickets, state can exceed 24 MB — four times the server's 6mb body limit. In practice, persistence stops working at roughly 30–40 evidence-bearing tickets, and it stops silently. This is the single most important architectural reason to move attachments out of the state object.

Deployment reality

The application ships as a static file and a Node process. There is no container definition, no process manager, no reverse proxy, no TLS termination, no health check outside the app, no graceful shutdown handler and no environment separation. app.listen() binds all interfaces by default. CORS is *, which is harmless only because there are no cookies to steal — and dangerous the moment sessions are introduced.

The database connection is a Supabase pooler URL with ssl: { rejectUnauthorized: false }. That disables certificate validation: the connection is encrypted but not authenticated, so it cannot detect a machine-in-the-middle on the path to the pooler. Supabase requires TLS; it does not require you to stop verifying it.

Evidence · exact source lines, placeholders absent

PostgreSQL reports a syntax error at or near "," or at end of input. The rejection happens inside ensureDefaultAdmin(), which runs before app.listen(). The promise rejects, the startup .catch() logs one line and exits with code 1. Nothing listens on port 3000. The front end hides this well because it defaults to local mode; the failure only becomes visible when someone enters the API URL and presses “Test backend connection”.

Root cause hypothesis

Zero occurrences of $1–$n in the file, while every query retains its parameter array, is the signature of shell interpolation during file generation (for example, a heredoc or echo where $1 expanded to the empty string). The fix is mechanical but incomplete on its own: add a startup smoke test that executes one parameterised query against a disposable schema, so this class of defect cannot ship again.

Secrets · immediate action

.env contains a live PostgreSQL superuser connection string and the bootstrap administrator password. Both are in plaintext, in a folder with no .gitignore, and the credentials are reproduced in this review's source but deliberately redacted here. Rotate the database password and the admin password now, then store them in a secret manager and commit only an .env.example with placeholder values.

Model 03 · Domain & data

One object doing the work of nine tables

The front end stores simulator state, tickets, timelines, evidence and audit entries inside a single mutable object. The database mirrors that shape. The result is fast to prototype and impossible to query, audit or grow.

The domain has nine distinct concepts: identity, asset, detection, alert, evidence, case, case event, attachment and audit event. The as-built system collapses them into two: a global simulator_state row and a wide tickets table. Everything else — the timeline, the report, the observed IP, the scenario link — lives inside JSON columns or free text. That is why the product can demonstrate a workflow but cannot answer a question like “show me every credential-stuffing alert on the Web Portal segment last month, and the median time to containment.”

Why this shape fails

A single object cannot be partially updated without reading and rewriting it. It cannot enforce that a closed case has a root cause. It cannot page, filter or aggregate. And because the object contains every screenshot, its size grows linearly with evidence: the transport limit becomes a functional limit on how many cases the product can remember.

Three model fixes that unlock everything else

1 · Time

Store every instant as timestamptz in UTC and serialise as ISO-8601. Render local time only in the presentation layer. The current mix of toLocaleTimeString(), toLocaleString() and epoch milliseconds makes the data unsortable across timezones, unusable in SQL and impossible to correlate with real telemetry. A case that cannot be ordered in time is not an investigation record.

2 · Identity

A ticket must reference a reporter and, once triaged, an assignee. Today the reporter is a free-text contact string and the assignee does not exist. That single omission removes ownership, workload balancing, handover, SLA attribution and every “who changed this?” question an auditor will ask. The PIN should become a verified channel (email magic link or one-time code), not a shared secret printed on screen.

3 · Evidence

An attachment is metadata plus bytes. Store the bytes in S3-compatible object storage (or IndexedDB blobs in a local-first build), the hash and MIME type in the database, and a short-lived signed URL in the UI. This removes the 6 MB ceiling, makes evidence tamper-evident, enables retention rules, and shrinks state from megabytes to kilobytes. It also makes the application portable to a purely client-side rebuild, where attachments are blobs in IndexedDB rather than base64 in a JSON document.

Migration path

You do not need to migrate existing data to improve the model. The simulator is a training environment with synthetic cases; the correct move is a clean schema, a seed script, and an export of old reports as static artefacts. Preserve the shape of the report, not the rows that produced it.

Model 04 · Behaviour & detection

The three-second world

A single interval function is the entire physics engine. It generates two series, ages threats out after ninety seconds, fires two threshold alerts, and occasionally invents a new incident when the analyst is bored.

The heartbeat

tick() runs every 3,000 ms. Each tick produces one sample for each metric, one synthetic allow event, one event per active threat, and a full re-render of every view. The chart keeps the last 16 samples, so the visible window is 48 seconds; a threat lives for 90 seconds and therefore outlives the graph that first showed it.

tick() every 3,000 ms:
  drop threats where (now - t0) > 90,000 ms
  for each threat whose segment is UP:
      f = 1 - age / 90,000
      if scenario.k == "log":  loginPressure += 38 * f
      else:                    speedDrop     += (slow ? 58 : 44) * f
  logins = 1 + rand(0..3) + round(loginPressure)
  speed  = max(5, round(92 + rand(0..8) - speedDrop))
  push {logins, speed}; keep 16 samples
  append ALLOW event; append one event per threat
  if logins > 10 and not alerted: notify "above threshold"
  if speed  < 50 and not alerted: notify "below threshold"
  if rand() < 0.02 and no threats: inject a random scenario
  if unlocked and idle > 5 min: lock
  render KPIs, charts, feed

Detection model: as-built versus target

As built
  • Two static thresholds.
  • Three hard-coded scenarios.
  • No correlation across events.
  • No asset context or criticality.
  • No suppression or deduplication.
  • No MITRE ATT&CK mapping.
  • No historical alert store.
  • No rule authoring surface.
Target
  • Detection-as-code: YAML/JSON, versioned.
  • Threshold, sequence, absence and correlation operators.
  • Asset and identity enrichment before scoring.
  • Risk = severity × asset criticality × confidence.
  • Deduplication key and suppression windows.
  • Every detection maps to MITRE technique(s).
  • Alerts persist independently of the case.
  • Backtest harness with fixture events.
Design principle for the rebuild

Do not make the simulator “more realistic” by adding randomness. Make it more deterministic. A seeded generator, a scenario clock and injectable fixtures give you reproducible demos, fair grading and testable detection logic. Randomness is a demo feature; determinism is an engineering feature. The current build uses Math.random() in at least nine places, which makes every screenshot, score and test non-reproducible.

Case state machine

The golden path, step by step

  1. Signal. A scenario is injected. Within one tick the failed-login series rises above 10/min or throughput falls below 50 Mbps. The KPI turns red and, if an analyst is unlocked, a notification fires with sound and vibration.
  2. Notice. The feed prepends an event carrying the scenario key, segment, source IP, port, action and severity. The chart plots the sample and enlarges the point when it carries an incident.
  3. Inspect. Clicking Inspect pins the sample, opens a detail card and draws an amber marker on the graph. The card explains the symptom, the suspected source and the graph position.
  4. Research. A modal supplies the concept, how to read the relevant log, and a three-item checklist. No answers; only framing.
  5. Investigate. The lab lazily generates a mock login table, network table and user directory. For credential stuffing it contains 22 failures from one IP and one success immediately afterwards — the evidence needed to distinguish attack from typo.
  6. Assess. Five questions cover diagnosis, attribution, compromise, containment and prevention. All five must be answered. A perfect first pass scores 100; every wrong answer costs 10 and the penalty persists across retries.
  7. Attribute. Resolution removes the live threat, records the skill and concept on the ticket, and writes an audit line.
  8. Close. Four fields — root cause, action taken, systems impacted, prevention — unlock the closure. The system generates a plain-text report containing the case type, urgency, issue, analysis, timeline and skill.
  9. Archive. Case History re-renders every closed report. Bulk export concatenates any selection or all closed cases into one file.

Case study · 04:12, the credential-stuffing ticket

04:12:03. The simulator injects bf on Web Portal. Source 203.0.113.50. The next tick produces 39 failed logins per minute; the KPI crosses its threshold. Because no analyst is unlocked, no notification is sent — the only cue is a red number on a dashboard nobody is watching.

That final sentence is the case for a real evidence model. An investigation record that cannot reproduce its own evidence is a narrative, not an audit artefact.

Evidence pipeline

There are two capture paths. The user may upload an image, paste from the clipboard, or grant screen capture; the image is drawn to a canvas at a maximum width of 900 px and encoded as JPEG at quality 0.6. Separately, an analyst can click “Capture screenshot to ticket”, which composes an SVG containing the alert text and both charts, rasterises it through an Image, and feeds it through the same encoder. Both paths end in a base64 data URL stored on the ticket and broadcast to every tab.

Evidence quality

The second path re-encodes a vector composition as a lossy JPEG, embeds it in state, and then loses the source graph when the sample window rolls over. The evidence is legible but not evidentiary: no hash, no capture timestamp, no chain of custody, no retention, no redaction. For a training tool that is acceptable; for anything that resembles a real SOC it is disqualifying.

Cross-tab collaboration

BroadcastChannel('socsim') gives a convincing multi-window demo: two tabs share tickets and threats, and a new ticket in one raises a notification in the other. It is not collaboration. There is no identity, no presence, no locking, no merge and no ordering guarantee beyond a numeric revision. Two analysts editing different tickets can overwrite each other because the unit of synchronisation is the entire world, not the record.

What to preserve

The workflow itself. The order — signal, inspect, research, lab, assess, attribute, close, export — is exactly the loop a junior analyst needs to internalise. Rebuild the machinery underneath it, but do not redesign the pedagogy without a reason.

Model 06 · Threat & trust

The mock SOC is less protected than its incidents

A security trainer that trusts the browser, exposes every case to anonymous callers, stores a password in plaintext and executes state-derived markup is teaching the wrong lesson by example.

Trust boundaries

There are four boundaries and only one is enforced. The browser is treated as fully trusted: it decides who is an admin, which role to request, what a status may be and whether evidence exists. The API is reachable by anyone who can route to it, with CORS open to every origin. The database is reachable with a superuser credential embedded in the application folder. Only the last boundary — TLS to the pooler — exists, and its certificate is explicitly not verified.

Findings register

Severity reflects consequence in a deployed, shared environment. A classroom demo on localhost reduces likelihood but not design debt.

CriticalC-01

The API cannot start

Every SQL placeholder is missing. Fourteen statements fail to parse; startup exits before listening. Persistence, authentication and health are all unavailable, and the failure is invisible until someone configures the backend URL.

Fix — Restore $1…$n, add a boot smoke test against a disposable schema, and fail the build — not the process — on query parse errors.

CriticalC-02

Live credentials in plaintext

.env holds a PostgreSQL superuser URL and the bootstrap admin password. The folder has no version-control ignore rules. Anyone with file access, a backup, a screen share or a copied project archive has the database.

Fix — Rotate both credentials. Create a least-privilege database role. Move secrets to a manager. Commit .env.example only. Add secret scanning to CI.

CriticalC-03

Anonymous read/write of the entire system of record

GET /api/state and POST /api/state have no authentication or authorisation. A single unauthenticated request returns up to 200 tickets with PINs and screenshots. A single POST can replace the world and wipe the audit log.

Fix — Require a session on every route. Authorise per object. Scope by tenant. Make audit append-only. Never return PINs in bulk. Add rate limits and request size limits per route.

CriticalC-04

Access control is a prop

The admin PIN is the literal string '0000', compared in browser memory. The server accepts a client-declared role. There is no session, no token, no server-side permission check and no attribution. Locking the UI changes nothing an attacker can rely on.

Fix — Use an identity provider or per-user credentials with server-side sessions (HttpOnly, Secure, SameSite). Enforce role checks server-side on every request. Add step-up authentication for destructive actions.

CriticalC-05

Persistence dies silently at the evidence ceiling

Full state — including base64 screenshots — is POSTed on every mutation under a 6 MB body limit. Once the workspace accumulates roughly 30–40 evidence-bearing tickets, the request exceeds the limit, fetch rejects, and catch(_){} discards the error. The UI still claims an API target is set.

Fix — Store evidence as objects with metadata references. Sync deltas, not worlds. Surface sync state per record and show a persistent failure banner with retry.

CriticalC-06

Stored cross-site scripting through state fields

Several values are interpolated into innerHTML without escaping — notably the screenshot URL (<img src="${t.shot}">), ticket and scenario identifiers, and alert names. Because POST /api/state is anonymous, an attacker can store a payload such as x" onerror="… and execute script in every analyst's browser. No Content-Security-Policy is set.

Fix — Render through a framework that escapes by default; never build event handlers from strings; validate and constrain URLs to data:image/* or signed storage URLs; add a strict CSP with nonces.

HighH-01

Whole-world overwrite with no conflict detection

The unit of synchronisation is the entire state. rev is generated but never compared server-side. Two tabs or two analysts can silently overwrite each other's tickets, statuses and lab results.

Fix — Per-record optimistic concurrency (version or updated_at), field-level patches, and a merge policy that rejects stale writes with a conflict response.

HighH-02

Identifier collisions and four-digit secrets

Ticket references use four random digits (9,000 values) and the primary key is that reference. The upsert is ON CONFLICT (id) DO UPDATE, so a collision silently overwrites an existing case. The follow-up PIN has 10,000 values with no attempt limit.

Fix — Opaque UUID primary keys; human references from a per-year sequence; collision-proof insert; six-to-eight-digit one-time codes with rate limiting and expiry.

HighH-03

Time is stored as prose

Timestamps are produced by toLocaleTimeString() and toLocaleString() and stored as text. They carry no date, timezone or offset. Sorting, filtering, SLA calculation and correlation with external telemetry are impossible.

Fix — timestamptz in UTC; ISO-8601 on the wire; localise only at render time; store the user's timezone on the session, not in the record.

HighH-04

The audit log is overwritten, not appended

On every sync the server executes DELETE FROM audit_logs and inserts the latest 50 client strings. Actor, object, action and outcome are absent. The trail is destroyed by the very act of persisting it.

Fix — Append-only table with database-enforced immutability, actor and request metadata, before/after snapshots for mutable objects, and retention independent of the case.

HighH-05

No schema, no migrations, no constraints

Five tables are assumed to exist. The repository contains no DDL, no migration history, no foreign keys and no indexes beyond the primary keys. A fresh environment cannot be provisioned from source.

Fix — Versioned migrations in source control, a seed script, enforced constraints, and a CI job that provisions an empty database and runs the app's queries against it.

HighH-06

Every tick rebuilds every view

renderAll() is called on each mutation and again inside tick() for charts and feed. Five views are re-rendered from strings every three seconds, including Case History and all base64 images. Focus is restored by a hand-written shim; the archive search input has no ID, so it loses focus on every keystroke.

Fix — Component-level reactivity keyed by record identity, memoised selectors, virtualised lists, and no re-render of inactive routes.

HighH-07

Idle lock depends on the simulator running

The five-minute auto-lock is evaluated inside tick(). Pausing the simulation disables the lock indefinitely. The unlock flag is global across Admin, Ticket Manager and Case History, so one unlock exposes every privileged surface.

Fix — Session expiry enforced by the server and by an independent client timer; per-route authorisation; re-authentication for destructive actions.

HighH-08

No hydration, no recovery

The UI only pushes. It never loads from the API, and nothing is written to localStorage or IndexedDB. A refresh erases tickets, labs, notifications and the user's follow-up references. The database is a write-only archive nobody reads.

Fix — Local-first persistence with an explicit sync engine, or server-authoritative state fetched on boot. Both need versioning, migration and a visible sync indicator.

HighH-09

The lifecycle is advisory

Status is a free-text column. Any transition is accepted, including Triaged to Resolved or Closed to anything. New tickets are hidden from the manager, so the KPI and the work queue disagree. Service requests are routed through incident labs and demand a root cause.

Fix — Explicit transition table enforced in one domain module and in the database; separate SR and INC closure criteria; show every open item in one queue.

HighH-10

Alerts expire before the work does

Threats are deleted after 90 seconds and never persisted. The graph shows 48 seconds. A case closed five minutes later has no machine record of the signal that opened it, only a sentence in the timeline.

Fix — Persist alerts and evidence independently of the simulator; keep the training clock, but write immutable alert records with first/last seen and raw samples.

HighH-11

No ownership, SLA or operational metrics

There is no assignee, queue, due time or escalation. MTTD, MTTR, backlog age, false-positive rate and lab completion are not measured. The product cannot answer whether it is working.

Fix — Assignee and team fields, SLA policy by priority, event-sourced timestamps, and a metrics view derived from case events rather than hand-counted.

HighH-12

Evidence has no chain of custody

Screenshots are lossy base64 strings. There is no hash, MIME type, size, capture time, uploader or access log. Evidence can be replaced by any state POST without detection.

Fix — Immutable object storage, SHA-256 on write, metadata row, signed access, and an audit event per read or download.

MediumM-01 … M-12

M-03 User tickets default to a scenario by segment, producing mismatched labs. M-04 A global pre object leaks scenario context into the next ticket. Clutter and minor defects

Duplicate controls (metric filter in two places, admin theme bar in three views), a dead “future backend” field, a KPI that counts hidden tickets, a new AudioContext per beep, silent 200-ticket truncation, and feedback IDs derived from array length. Individually cosmetic; collectively they make the console feel less trustworthy than it is.

Fix — One control per concern, remove unimplemented affordances, derive counts from one selector, pool audio, paginate with an explicit total, and use generated IDs.

Data protection and privacy

The dataset is synthetic by design, but the product invites real screenshots, real names and real contact details. That turns a training tool into a personal-data processing system with none of the obligations implemented. Before any shared deployment: classify the data, minimise collection (no free-text “contact” if an account exists), redact screenshots on upload where feasible, set a retention period (90 days is a reasonable default for training evidence), encrypt at rest, restrict download to the reporter and assigned analysts, and log every access. Never point the simulator at production telemetry.

Model 08 · Target platform

A production-shaped training system

Not a real SIEM, and not pretending to be. A system with real identity, real persistence, real evidence handling and a detection pipeline that can be explained, tested and taught.

Design principles

  1. Local-first, collaboration-optional. The simulator must be fully usable with no server. Collaboration is an additive tier, not a prerequisite.
  2. Deterministic by default. A seed controls all generation, IDs and question order. Any demo can be replayed exactly.
  3. Domain before screens. Cases, alerts, evidence and events are modelled once and rendered many ways.

  5. Every state change is an event. Status, assignment, score and report generation append to a log; current state is a projection.
  6. Teach the trade-off. Where the simulator simplifies reality, it should say so in the UI and in the report.

State, persistence and the simulation worker

Three stores, three lifetimes. The domain store holds cases, alerts, segments and content versions and is written through repositories to IndexedDB. The ephemeral store holds the live sample buffer, hover state, toasts and the current selection; it is never persisted. The session store holds the current user, role, theme and AI consent; it is persisted separately so clearing case data does not sign the user out.

The worker is the clock. It owns a seeded PRNG, a monotonic tick counter and the scenario schedule. It emits typed messages such as {type:'sample', series, value, ts} and {type:'threat', action:'inject'|'expire', threat}. The UI never calls Math.random(). A visible “seed” field and a replay button make every demo reproducible.

Persistence is a repository, not a side effect. caseRepo.save(case) writes the record and appends an event in one IndexedDB transaction. evidenceRepo.put(blob, meta) stores bytes and hash. Components never touch Dexie directly; this keeps the same domain code portable to a server later.

Why a worker

The current app runs its clock on the main thread and rebuilds the DOM every three seconds. Moving generation into a worker isolates CPU work, survives heavy rendering, and makes the simulation testable in isolation. It also enforces the boundary: the worker cannot read the DOM, so it cannot accidentally depend on the UI.

Runbooks

RB-01 · App will not load

  1. Check the browser console and the static host status.
  2. Verify the bundle hash matches the release tag.
  3. Clear the service worker and hard reload.
  4. Check IndexedDB quota; a full disk can block startup.
  5. If a migration failed, restore the previous release and export local data.

RB-02 · Sync divergence

  1. Pause writes and export every local case.
  2. Compare record versions, not global revisions.
  3. Prefer the newer event per case; never merge whole worlds.
  4. Record the reconciliation in the audit log.

RB-03 · Evidence store full

  1. Report quota usage and the largest attachments.
  2. Export and archive closed cases.
  3. Apply retention: delete evidence beyond 90 days.
  4. Never delete an attachment referenced by an open case.

RB-04 · Suspected credential exposure

  1. Rotate the database and admin credentials.
  2. Revoke sessions and API keys.
  3. Preserve audit and access logs.
  4. Notify the data owner; assess the exposed record set.
